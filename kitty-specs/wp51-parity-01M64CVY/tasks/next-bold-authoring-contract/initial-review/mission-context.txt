# Mission Specification: WordPerfect 5.1 parity

**Mission Branch**: `feat/wp51-parity`  
**Created**: 2026-10-29  
**Status**: Scope confirmed; discovery checkpoint recorded; detailed parity research remains open
**Mission**: `wp51-parity-01M64CVY` (`01M64CVYYRTDKBCYZ56H6XNTEQ`)  
**Input**: Lynn confirmed two missions: complete WP 5.1 DOS parity first, then
modern conveniences including PDF; original file formats remain unchanged.

## Confirmed intent and boundaries

For writers and original WP 5.1 users, opening or creating a document on Linux
must provide the original application's commands, formatting semantics,
automation, files, and printed results. Reveal Codes means the original editing
function, not merely a visual representation of formatting. Native documents and
companion artifacts must remain interoperable with the original application.

This is M1 of the [two-mission charter](../../.kittify/charter/charter.md).
PDF and newly selected modern conveniences belong to M2 after parity acceptance.
Existing backup, mouse, configuration, and other original functions remain M1.
Intermediate releases are milestones within M1, not a reduced definition of parity.
User confirmation is recorded in `decisions/DM-01M64CWKX056PQDXX2D3QW7QR0.md`.

The [compatibility contract](../../docs/compatibility.md) is binding. The exact
reference executable is now fingerprinted and its Help date confirmed; no
Wordling compatibility is claimed. The [selected primary target](../../docs/decisions/0001-reference-release.md)
is plain 5.1 DOS, U.S. English dated 1992-03-09, without excluding other original
language/character obligations.
The downloaded manuals span several publication dates and must be reconciled.

`main` is the GitHub integration/PR destination. Spec Kitty's `meta.json`
`target_branch` is `feat/wp51-parity`, the mission's planning placement; these are
distinct surfaces in this runtime. No mission merge or implementation acceptance
is requested by starting this specification.

## User Scenarios & Testing *(mandatory)*

Priorities establish sequencing, not optional scope. Source groups and initial
acceptance probes are in the [inventory](../../docs/research/feature-inventory.md).
These user-story scenarios are requirements. Bounded command-level original observations are linked below; no Wordling scenario has been verified.

### User Story 1 — Keep original documents usable (Priority: P1)

A user retrieves, edits, and saves original documents without conversion or loss.

**Independent Test**: Execute the same bounded edits in Wordling and the declared
WP 5.1 reference, inspect native data, then retrieve and print both results in WP.

**Acceptance Scenarios**:

1. **Given** a valid original file, **when** it is opened and saved without edits,
   **then** the output bytes are identical (FC-002).
2. **Given** text containing attributes and an opaque valid structure, **when** a
   supported edit is made elsewhere, **then** unrelated content and relationships
   survive and WP retrieves the file without repair or feature loss (FC-003/004).
3. **Given** a new document, **when** the user saves through the original workflow,
   **then** WP 5.1 retrieves, edits, prints, and saves it, and Wordling reopens it.
4. **Given** a failed or unsafe save, **when** the error occurs, **then** the
   original file remains intact and the user receives an explicit failure.

### User Story 2 — Work through the original editor (Priority: P1)

An experienced user uses the original keys, prompts, menus, selection, search,
Reveal Codes, and editing semantics without relearning the word processor.

**Independent Test**: Replay a recorded reference session and compare command
state, cursor position, code effects, prompts, selections, and saved results.

**Acceptance Scenarios**:

1. **Given** a formatted paragraph, **when** Alt-F3 is used and a code is deleted,
   **then** both panes reflect the same change and the saved file matches its
   documented semantic effect (REF51 pp. 112-113, 560-562).
2. **Given** a code embedded in text, **when** typeover reaches it, **then** the
   code remains and inserted characters follow original behavior (p. 695).
3. **Given** three deletions made with declared commands, **when** the original
   Undelete choices are used, **then** text and code restoration match the
   reference command-specific behavior (p. 697).
4. **Given** nested menus, both document screens, and search prompts, **when**
   original navigation/cancel commands are replayed, **then** document and prompt
   state match the reference, including unchanged state after cancellation.

### User Story 3 — Format and print the same document (Priority: P1)

A user produces the original formatted pages, including advanced structures.

**Independent Test**: Compare page boundaries, glyph positioning, codes, and
printer output with fixed page settings and identical declared resource metrics.

**Acceptance Scenarios**:

1. **Given** fixed printer/font resources and layout settings, **when** margins,
   tabs, columns, headers, notes, and hard/soft breaks are combined, **then**
   pagination, numbering, and printed positions agree with the reference.
2. **Given** a table, equation, and anchored graphics box, **when** they are edited
   and printed, **then** structure, calculations, placement, wrapping, and saved
   representation retain original semantics.
3. **Given** original index/contents/authorities marks and subdocuments, **when**
   generation runs, **then** entries, order, numbering, and references agree.
4. **Given** selected original printer resources, **when** print-to-disk is used,
   **then** the documented original printer-language output is retained.
5. **Given** a graphics-capable reference preview, **when** preview is opened on
   Linux, **then** the original page-inspection functions have a tested Linux
   presentation; terminal limitations cannot silently remove this obligation.

### User Story 4 — Automate and manage work (Priority: P2)

A user reuses original macros, merge files, styles, dictionaries, spreadsheet
links, and utilities without migrating those artifacts to new formats.

**Independent Test**: Run fixtures and keystrokes through both applications,
compare generated files and results, and reopen them in the original app.

**Acceptance Scenarios**:

1. **Given** an original macro or merge workflow, **when** it is executed or
   edited, **then** commands, variables, expressions, prompts, output, and errors
   agree with the declared reference (including native serialization).
2. **Given** text, language resources, sort keys, or a spreadsheet link, **when**
   original language/data tools operate, **then** original results and update
   behavior are reproduced using declared resources.
3. **Given** backup, configuration, utility, and file-management workflows,
   **when** exercised on Linux, **then** original artifact semantics remain and
   platform adaptations are documented and tested.

### Edge Cases

- Truncated prefixes, invalid pointers, cyclic packet chains, bad lengths,
  mismatched delimiters, deeply nested text, and malformed encrypted data.
- Unrecognized valid code/packet types; edits that invalidate opaque references.
- Paired attributes crossing selections, deletion boundaries and subdocuments.
- Typeover at code boundaries, cancellation during prompts, and deletion history.
- Unsupported characters, missing fonts/dictionaries/graphics, and printer changes.
- Hard/soft pages, tables spanning pages, note continuation, and field regeneration.
- Wrong passwords, interrupted writes, disk exhaustion, permissions, and shared
  file conflicts. No failing path may damage the original or report false success.
- Terminal resize, unavailable modified function keys, and graphics presentation.
- DOS paths, 8.3 names and case handling versus Linux paths; explicit mappings
  must be resolved before compatibility claims for those workflows.

# Implementation plan: WordPerfect 5.1 parity

Branch: `feat/wp51-parity`. Date: 2026-10-30. Authority: [spec](spec.md), [research checkpoint](research.md), [domain model](data-model.md).

## Delivery strategy

M1 remains complete WP 5.1 DOS parity. Start with a bounded native preservation milestone while research closes the rest of the catalogue. This plan is an architecture and sequencing baseline, not permission to guess undocumented semantics. The first task queue covers foundations and explicit investigations; subsequent implementation packages must be authored from their outputs before full M1 acceptance. Completing this queue alone cannot satisfy SC-001–005.

Use the pinned Go module and Bubble Tea version already in go.mod; Linux target. Do not update dependencies for scaffolding. Use Go testing and fuzzing for native boundaries, the existing Python reference runner for the original executable, and stable inventory/scenario IDs for differential checks. Native WP documents/companions are the only persistent product formats; diagnostic test manifests are project tooling, never required document sidecars.

## Context and component boundaries

```mermaid
flowchart LR
    User[Writer] --> TUI[Bubble Tea session and prompts]
    TUI --> Commands[Original editing commands]
    Commands --> Document[Document characters and codes]
    Document --> Native[Native framing and exact bytes]
    Native --> Files[Original WP files]
    Document --> Layout[Layout with declared resources]
    Layout --> Output[Original preview and print output]
    Macro[Macro execution] --> Commands
    Merge[Merge execution] --> Document
    Resources[Printer and language resources] --> Layout
```

Dependency direction is inward toward document semantics. No terminal dependency in native parsing, document editing or layout. Macro and merge execution keep distinct state machines despite shared token vocabulary. See `data-model.md` for invariants. Proposed packages are created only when their bounded work begins:

- `internal/wp51`: exact byte image, validated native framing, original character/code identity and preservation. No filesystem replacement or terminal code.
- `internal/document`: editable semantic positions, paired-code relationships and command-specific Undelete; mutations must declare supported structures.
- `internal/editor`: session, original commands/prompts/modes and both document screens. Uses document services; never edits serialized bytes independently.
- `internal/tui` and `cmd/wordling`: Bubble Tea rendering, input adaptation and application composition.
- `internal/storage`: safe native read/write transactions and original save decisions supplied by editor. Retains existing files on failure.
- `internal/layout`, `internal/resources`, `internal/printing`: original geometry/resource interpretation and output, independent of terminal wrapping.
- `internal/macro`, `internal/merge`: original companion decoding and execution, with explicit call/loop/handler and record/copy/page contexts.
- `testdata` and test-only fixture manifests: provenance-approved native fixtures selected from existing original runs. Reference binaries remain ignored and external.

No plugin framework, generalized workflow engine, Unicode-only canonical document, or rewritten document format is introduced. Public Go APIs are unnecessary initially; keep packages internal until real consumers justify stability guarantees.

## Native preservation contract and first milestone

First implement framing and no-edit pass-through only. An immutable owned byte image is authoritative. Validated spans retain native order and offsets; semantic decoding is additive. Expose parsing support explicitly: recognized, opaque-but-preserved, malformed/refused. Do not treat unknown data as empty content. A structurally framed file is not necessarily semantically editable.

The first reader contract must document SDK51 field offsets, integer widths/endian rules, checked arithmetic, packet/index traversal, cycle/truncation handling and prefix/body bounds before coding. WP01 selects fixtures and records this contract. Until validated, unsupported variants are refused with typed errors; they stay in the M1 backlog. Native no-edit export copies the exact owned image, including uninterpreted data and trailing bytes; it never reconstructs headers or timestamps. Source buffers and exported buffers cannot mutate internal state.

Safe filesystem replacement follows as a separate package. Candidate bytes and failure paths are tested before any original-app retrieval. No general edit writer is authorized by a pass-through test. Semantic writes require their own scenario contracts, byte preservation checks and original retrieval/edit/print/save acceptance.

## Verification strategy

- All changed Go: gofmt, `go build ./...`, `go test ./...`, `go vet ./...`. Reader packages require truncated/oversized/cyclic/framing-negative tests and a reproducible fuzz invocation with declared budgets. Set budgets in WP01 from format bounds and measured harness behavior; no unmeasured product performance claims.
- Accepted no-edit fixtures: compare bytes, length and SHA-256; test opaque span/trailing-byte preservation and caller buffer isolation. Self-generated fixtures supplement rather than replace original-produced fixtures.
- Filesystem safety: inject failures before write, during candidate creation and before replacement; verify original bytes and absence of false success. Concurrent source change and symlink/path policy are explicit contracts, not guessed Linux adaptations.
- Each supported semantic edit: original command transcript, same declared inputs/resources, native invariants plus original reopen/edit/print/save. Expect different unrelated timestamps only when the original scenario explicitly documents them; never normalize raw evidence.
- Existing catalogue checks: `python3 scripts/render-inventory.py --check` and `python3 scripts/render-scenarios.py --check`. Python changes additionally compile; original reference probes run only for new questions or changed harness behavior.
- Terminal interaction checks compare command/session state independently of visual snapshots. Original print-to-disk, preview and utilities remain M1; PDF stays M2.

Mixed manual editions and current FreeDOS/printer limitations remain declared. Expanding profiles is a research task, not a baseline replacement. Encryption, nested packets, alternate characters and resource dependencies may narrow which files are initially safely interpretable; unsupported inputs produce explicit refusal without modifying their source. Performance/size targets and full layout tolerances remain gated research outputs before those implementations. Proprietary manuals/resources never enter the public repository.

# M1 domain model — discovery checkpoint

These are conceptual boundaries for planning, not a finalized on-disk schema or an implemented API. WP native files remain unchanged.

| Entity | Identity / state | Relationships and invariants |
| --- | --- | --- |
| Native image | Exact bytes, original file identity, validated bounds | Owns prefix, index/packet spans and body spans; no-edit serialization returns exact original bytes. Opaque spans stay intact. |
| Document | Native image plus interpreted editable structure | Original characters, text/code positions, paired codes and nested text areas; semantic support is explicit, never inferred from parse success. |
| Edit command | Original command, cursor/selection, declared preconditions | Produces a bounded document change or explicit refusal. Normal and Reveal Codes views share the same document and position mapping. |
| Undelete history | Up to three original deletion entries | Captures command-specific restoration content and code behavior, distinct from future modern undo. |
| Session | Documents/screens, modes, prompts, initial settings | Owns command routing; terminal cells display state without defining layout or native identity. |
| Resource profile | Fingerprinted printer/font/character/language settings | Determines layout and printing comparisons; executable date alone is insufficient identity. |
| Layout result | Document revision plus resource profile | Contains lines/pages/glyph placements used by original preview/printing; invalidated by relevant edits or settings. |
| Macro execution | Program, call stack, loops, handlers, variables | Uses original WPM representation. Loop NEXT/BREAK and error scope require explicit context. |
| Merge execution | Primary stack, secondary records, copy state, page mode | Distinct from macro execution; global PAGE state crosses nested primary/secondary return boundaries as observed. |
| Save transaction | Source identity, candidate bytes, destination decision | Refuses unsupported changes or unsafe replacement; failure preserves existing file. Original prompts are session behavior. |
| Acceptance scenario | Stable CMD51 ID, inventory links, manual citations | Separates authored expectations, original observation, implementation and differential verification. |
| Reference run | Recipe, executable/resources/environment, captures and hashes | Supplies bounded observations; never proves Wordling behavior unless Wordling was separately exercised. |

Translation boundaries: native bytes → validated spans → semantic document; document/session → terminal view; document/resources → layout/print; original automation tokens → context-specific execution. Each boundary needs its own failure behavior and evidence. Unknown bytes must never become silently disposable semantic defaults.

# Permanent compatibility contract

These are project requirements, not claims about an implemented application.
They apply to both missions.

| ID | Obligation | Acceptance evidence |
| --- | --- | --- |

| FC-002 | An untouched valid supported input saves byte-identically. | SHA-256 and direct byte comparison, including prefix packets and embedded data. Opening must not silently normalize the source. |
| FC-003 | Editing preserves unrelated codes, packet content, embedded resources, and semantic relationships. | Targeted edit fixtures; binary differences explained; original-app retrieval and behavior checked. Offset/length changes are permitted when required, arbitrary normalization is not. |
| FC-004 | Unknown or not-yet-supported structures are preserved. Unsafe edits/saves fail explicitly before replacing the original. | Opaque-code and packet fixtures, reference checks, rejected-edit and failed-save scenarios with original bytes unchanged. |
| FC-005 | Original companion artifacts retain their original formats wherever the app reads/writes them. | Per-format fixtures and original-app checks for macros, styles, merge data, keyboard definitions, and user resources; scope expanded from manual research. |
| FC-006 | Characters preserve their WP character-set identities and round-trip. | Character-set corpus; unsupported input receives an explicit error or choice before modification, never silent replacement. |
| FC-007 | Native saves are independent of conversion through another word processor. | The Go format writer emits original-format data directly; external tools may be independent test witnesses only. |
| FC-008 | Original export/conversion and print-to-disk modes retain their documented formats and semantics. | Per-mode comparison against original output with encoding, resources, and conversion losses declared. These modes do not replace the native save format. |
| FC-009 | A failed save must not corrupt the existing file. | Tests for permissions, interrupted/short writes, full storage, and failed replacement; original backup conventions researched and preserved. |
| FC-010 | PDF is a new, optional M2 export. It never becomes the editable native document format. | M2 PDF acceptance tests against the shared layout output and native-file preservation checks. |

## Fidelity levels

Byte identity is required for no-edit native round-trips. After an edit, the whole
file need not have identical bytes: lengths, pointers, and related state may need
to change. Differences must be confined to the intended edit and required
structural updates, with unrelated data preserved.

Behavioral fidelity includes command sequences, prompts, code/cursor semantics,
selection, error handling, pagination, and rendered/printed results. A matching
screen alone does not establish format or behavioral compatibility.

Exact pagination needs a declared printer, font metrics, resources, settings, and
reference output. Linux printer delivery may differ operationally; document
layout or original print-to-disk bytes must not change without an explicit,
tested adaptation decision.

## Reference baseline and remaining installation work

- Primary documentary target: plain WP 5.1 DOS, U.S. English, 1992-03-09.
  See [ADR 0001](decisions/0001-reference-release.md). Selection does not narrow
  the original language/character compatibility obligations.
- The executable and 158 installed files are fingerprinted in
  [the baseline registry](research/reference-baseline.json). Fifty-three bounded original
  reference recipes have been repeated; Wordling and full scenarios remain unverified.
- The [current reference environment](research/reference-environment/README.md)
  uses FreeDOS 1.4 and a July 1992 text-only printer resource alongside the
  confirmed March program. Historical DOS and graphics/pagination profiles remain
  to be established; this is not an untouched March shipping-set claim.
- OS/emulator, keyboard, display settings, and filesystem behavior.
- Installed printer definitions, fonts, dictionaries, hyphenation resources.
- Repeatable input fixtures and keystroke captures with provenance.
- Differences between the 6/92 reference manual, the 11/89 workbook, and later
  toolkit documentation; record applicability rather than assuming equivalence.

Encrypted documents, graphics preview, legacy printer resources, DOS integration,
and resource licensing remain explicit research obligations. Uncertainty does not
remove them from M1 scope or establish support.

# Two-mission roadmap

## M1 — WordPerfect 5.1 parity

Status: starting. Complete original-app parity is the objective; an MVP is not
the acceptance boundary. Research, specifications, planning, and implementation
milestones all belong to this mission.

Suggested sequencing, subject to the implementation plan:

1. Reconcile manual coverage; identify and fingerprint a reference installation.
2. Establish original-format fixtures, lossless reading/writing, and safe editing.
3. Establish classic terminal interactions and Reveal Codes over the same model.
4. Implement formatting, fonts, pagination, printing, and document preview.
5. Implement structured documents, automation, language tools, and utilities.
6. Close all coverage gaps and run original-application acceptance scenarios.

Milestones are not additional missions. Ordering can change with dependencies.
Features discovered during manual study expand the tracked obligations rather
than disappearing outside a frozen short list.

Exit: complete inventory reconciliation; every obligation verified against the
declared original baseline; no unresolved destructive file or semantic mismatch;
documented compatibility limitations resolved or explicitly adjudicated by Lynn.

## M2 — Modern conveniences

Status: planned, not started; depends on M1 acceptance.

Confirmed scope: PDF export from document layout. Additional convenience features
remain candidates until selected. Existing backup, mouse, keyboard configuration,
and other original features must not be incorrectly deferred into M2.

Exit criteria will be specified at mission start. All permanent charter and
native-format requirements remain binding. Modernization cannot introduce a new
native format or require a Wordling sidecar to use a document.
