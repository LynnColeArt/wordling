## Decision recommended, not approved

Choose **operation-specific ASCII source AND target permission**, rather than
broadening shared CheckMutation. B's source-origin rule is CONDITIONAL on A:
prefer structural ASCII-only H1 if the already finite controls actually prove
nonempty H1 Save/clear/retrieve/next-operation with all72 closed facts; otherwise
use the existing loaded-empty birth lineage with ASCII-only descendants as a
bounded fallback, or leave mutation blocked. There is no permission grant now.

H1 here is the closed reordered e724/counter02, no-slack native field/graph family
actually observed in the four approved46v3 empty FIN exports. All four exports are
identical, not four new body/layout classes. Recon's108 sealed files and every
immutable source row in source-map.json were verified. Across the four PRE/FIN
72-field ledgers, the sole native change is packet6+8 01→02. The actual second Go
Q export starts from PRE/01, never FIN/02. Legacy117202 FIN and unresolved564 are
still read-only; old117201 !reordered remains independently admitted. A byte-value
exception cannot bridge these relationships.

Full-current-domain qualification would retain the existing shared gate and API,
but would grant ASCII/max-two-existing-Bold-body mutation, pair/block repairs and
all currently guarded history paths. It requires H1 Bold-bearing sources and
operation/history observations that do not exist. There is no general Bold
insertion API that could produce those sources. Copying C44's23 operations/14
classes/48 successful leaves would assume both source availability and output
classes, so that option is not the minimal justified next slice.

Structural ASCII-only H1 recognition is broader than PRESENT source proof:
nonempty H1 reloads have not been qualified. Restricting the existing private birth
lineage avoids treating a derived candidate as an independently qualified new
loaded source. Under that fallback, **Save As/reload of nonempty H1 is read-only until later
qualification**, even though continued typing before reload is permitted. Delete,
Backspace, block/Restore/Undelete and history initialization remain unavailable.
This user-visible partial capability must be explicit, not described as full
editing, no-history-as-empty, or complete reload parity. All gaps remain in M1.

## Actual API and invariant boundary

No public mutation signature needs replacement. Future implementation uses the
existing InsertASCII/TypeoverASCII and sole publishBody path. Its proposed private,
typed operation authorization is NEW work, not an API present today:

- Preserve existing full mutationAdmission/CheckMutation behavior and all old
  admitted families. NewHistory, checkDeletion, DeleteBlock/AnswerDeletion and
  Restore continue to require their existing full/history qualification.
- H1 permission is derived only from private valid loaded birth.originalImage:
  complete closed H1 facts, flags00 and empty original body. Parse of VALID empty
  H1 legitimately creates an eligible loaded birth; that is document-domain
  lineage, NOT filesystem/source-capability authority. Parse of a nonempty target,
  New, public wrapper assignment or an exported flag cannot rewrite the captured
  empty origin of an existing revision. New never creates H1. A newly parsed
  nonempty H1 has a different loaded origin
  and refuses this permission. Same-byte separately parsed images stay distinct.
- Every H1 ASCII source revision must share that origin, have only printable
  native ASCII tokens and the exact allowed current H1 field/graph relations.
  Existing MaxMutationBytes/MaxMutationTokens and cursor/revision/input checks
  remain. No new length policy is presented as an original DOS limit.
- The sole publisher must require source-state-bound typed operation authority,
  not a generic Boolean or reusable exported permit. It revalidates the TARGET
  under the same ASCII-only lineage/operation contract after parseRevision.
  It must never let deletion/Restore/generic publication borrow ASCII permission.
  Birth, OriginalExport, flags and unrelated bytes remain independently checked.
- Target change is the existing indexed OR08 plus intended ASCII body changes;
  all other prefix/cache/counter bytes are preserved. Counter02 is NOT advanced
  by a guessed algorithm. No body/code/equation/resource/relocation/hash algorithm
  or native serializer is added. All72 fields, pool/AFC/index/extent and reference
  constraints remain necessary; the decoder remains the actual wp51 reader.
- No-op/empty-input/same-byte paths still check operation authorization before
  returning unchanged native bytes/cursor/receipt. Refusals are atomic and typed.
  A proposed new UnsupportedMutationContext category may distinguish a known H1
  but unqualified origin/operation; its exact contract is future reviewed work,
  not a claimed existing category or a generic error bypass.

## Production callers actually traced

Approved36 b184 editor Text dispatch calls InsertASCII/TypeoverASCII directly.
Retrieve attempts NewHistory but leaves historyValid false on refusal; Text then
skips AfterEdit rather than inventing a stack. It still preserves old fragments,
unknown counts, buffer/source/revision identities. Mode/navigation are independent
of history permission; F10 exports the actual native candidate. Approved41
PreparePublication checks native framing, immutable source/target capability and
normal transaction guards, not CheckMutation. No new storage path is needed.

Approved37 d5c Model.resolve delivers Editing text to Session.Reduce; panes use
Present. Model.State delegates Session.Snapshot. Those actual snapshots have NO
ReadOnly/MutationAllowed flag and these host paths have no CheckMutation pre-gate.
Thus no genuine ordinary text-delivery blocker was found that requires G/H edits.
The current generic Editing/unknown-history presentation is not evidence of full
mutation qualification. The proposed core is not itself a UI or UX implementation.

Macro invocation/StartMacro compile separately; approved36's literal sink re-enters
ordinary Text. It therefore WOULD reach the same proposed native ASCII permission
in a normal loaded H1 context; no macro-specific permission/refusal is invented.
Native contract safety applies equally to this caller. Actual macro-H1 timing,
repeat/buffer/stop/original interaction is still unqualified and must not be
claimed from a direct producer or ordinary text PTY. No extra host guard or new
label is required by this decision; only an actual demonstrated integration/API
blocker would justify a later consumer-owned change.

Future core qualification must include a frozen real cmd/wordling composition
using the approved37/36/41 callers and new core, with actual normal native Save
outputs. A direct API producer alone is not app integration. The consumer's
normal supported dependency uptake, original macro-H1 and nonempty reload proof
remain explicit later obligations. Do not merge a moving G/H/E branch to get them.
