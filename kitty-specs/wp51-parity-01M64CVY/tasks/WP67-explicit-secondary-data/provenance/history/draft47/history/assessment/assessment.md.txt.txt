## The smallest useful semantic question

The observed result is `FILLED Alice\fEMPTY Bob`. This is a useful candidate for a separately reviewed, bounded source-backed evaluator contract: output must be computed from the admitted primary command spans and the bound secondary field-content spans, with the branch selected by the actual explicit empty span. Looking up a fixture's expected string by hash/path, substituting injected records, replaying a result image, or exposing the WP53 audit as an evaluator would not satisfy it.

This is an **evidence-supported candidate**, not authorization to make a Secondary Program from public Inspection fields. A design decision must explicitly state whether a closed explicit-field predicate can be proved without resolving universal record counts, and what source/target authority such a consumer carries. General count semantics are not logically required to decide this closed subset, but silently bypassing the existing refusal is not justified.

## Actual ordinary caller and output gaps

There is **no existing ordinary merge caller** in the inspected approved host source. An exact static search of immediate `.go` files in internal/editor, internal/tui and cmd/wordling finds no merge/native import, Merge/merge or CtrlF9/ctrl+f9/shift+f9 route. This is a static negative, not an app test. The Session Command and IntentKind enums likewise have no merge acquisition/evaluation intent. H66's real `macroStart` → runtime worker → `macroReply` → session/host IO path is specifically macro authority and cannot be relabelled merge execution.

The current ordinary editing route calls document printable-ASCII mutation. `document.InsertASCII`/`TypeoverASCII` validate every input byte as0x20–0x7e; they reject the0A/0C needed by all five observed outputs. NewDoc1 construction contains its own bounded native genesis0A, which is not a general HR/page writer or output import API. Existing deletion/history restoration preserves originally owned tokens; it does not authorize constructing merge result controls. `Document.Export` and ordinary F10 publication can preserve or save an authorized document, but cannot manufacture a new authorized merge result revision from an effects trace. Native parsing of arbitrary result bytes is not writer permission.

Thus there is currently no honest ordinary acceptance path from acquiring PRIMARY+SECOND, selecting an output document/screen, computing effects, materializing native result, and saving through F10. A prototype or CLI/demo-only interpreter would leave this host gap open. No such consumer is proposed as already existing.

The missing contracts are precise: ordinary merge invocation/file acquisition and cancellation/error behavior; source/run/role ownership across both inputs; target document/screen and revision binding; bounded execution and partial-effect/refusal policy; authorization for literal/field HR/hardpage/native output materialization and faithful metadata/formatter handling. Existing source observations do not prove original target overwrite/partial-output lifecycle, original merge UI prompts, arbitrary record counts/tails, whitespace/multiline/format-bearing fields, error recovery or physical pagination. Five original result images can validate a future output contract, but copying their metadata is not a writer algorithm.

## Why earlier macro/nesting evidence does not fill this gap

The retained automation inventory already distinguishes FOR EACH strings/expressions226/227 and nested NEXT228 as **macro** observations. They cannot establish native merge expression values, loop opcodes or coercion. Macro file BREAK229/230 ignores the command in those contexts; root-primary BREAK231 ends a copy and continues records; secondary BREAK232 leaves a partial second copy (`Hello Alice\n\fHello \n`). These differences forbid sharing a guessed generic BREAK policy. The origin of the last HR in232 is not independently established here.

Nested primary223–225/236 and nested secondary233–235 record persistent PAGE settings, current-record/replacement semantics and return behavior. Their canonical source/locators remain in the pinned automation contract; this assessment did not re-run them or broaden their claim level.
