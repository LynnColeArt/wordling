# Reveal Codes parity reconnaissance

Reveal Codes is implemented today for the supported native ASCII/Bold subset. Alt-F3 toggles a lower code stream derived from the same document/cursor as the normal text. The current UI is a bounded functional composition, not yet a faithful whole-screen WP5.1 clone. The next smallest useful improvement is **the missing active token/cell highlight in the existing lower Reveal stream**, while preserving the actual upper hardware caret. Do that before claiming a complete code catalogue or redesigning window/layout behavior.

This is read-only priority research, not task/design/implementation approval. No source/canonical/task/Op/VM/private media changed or new application/original run occurred. All38 obligations/91groups/36lessons/nested leaves/full M1 remain open. PDF/M2 is not advanced.

## Actual approved implementation

Immutable source proof pins approved37 dfd2df9d (model/runtime/current original comparison tests), approved47G3937a3d5 session presentation and approved46 document44aab36a cursor/Present, plus approved13 source18d6afe9,11 contract3fb4a5b8 and21 leavesd7b94b1f. Active48 source46afe is not inspected/used as authority. Any future H change must wait its independent approval and then bind its real source/API.

`Model.panes()` requests Session.Present(0,min(TokenCount,4096)). It refuses when gap>4096. The approved document Present indexes an already-validated immutable native Image and returns token-index/source-span values; it refuses the entire requested window if any token is Opaque. Cursor.Move likewise refuses crossing an Opaque token. It has no pagination, wrapping or terminal-cell model. ASCII and matched Bold On/Off are the only identified kinds; the rest of the native image remains retained for exact no-edit export. Opaque retention is not universal Reveal support.

The TUI independently constructs normal text with Bold ANSI styling and Reveal labels `[BOLD]`/`[bold]`. In normal text Bold codes consume zero columns; in Reveal they consume six label columns. It derives normal/reveal left clipping separately from gap-centered horizontal cell counts. It currently presents one text row per stream, not a multi-line scrolled code window. [Block] display markers and HistoryPreview overlays are view-only, not native tokens. Existing code does not visually select the current lower-pane token/cell.

`View()` currently places a product header at terminal row0, normal text at row1 and, when Reveal is on, an explanatory line at row2 then the Reveal stream at row3. Prompt/status/diagnostic lines follow and are clipped to terminal dimensions. The hardware cursor is deliberately placed in the normal pane at row1 in editing/deletion/history/wait states. It is **not absent** and is not moved into the lower stream. Existing tests prove the normal caret remains stationary across a Bold boundary and compare exact original text/cues; original_test.go explicitly excludes raster/row/layout parity. The README's4096-token fixed window, horizontal clipping, opaque-window refusal and no-pagination statements match the source.

No actual claim follows from the old README's now-historical statement that no New/macro route exists; those later features have their own approved work. Relevant Reveal renderer/Present facts above are taken directly from code, not that stale broader feature summary.

## Remaining gaps and useful later questions

Default split geometry/status/ruler fidelity is a separate bounded follow-up. The known default rows are usable evidence, but copying a fixture ruler line or inventing Pos/page/inch values would not be a faithful model. Document display metrics, original tab ruler derivation, custom colors/attributes and window settings need source/data contracts. Printed CPI/6LPI or document pagination are not terminal pane geometry.

Full code-label catalogue is separate. Appendix C and captured codes supply documentary/case leads, not authority to decode every Opaque payload or display its label. Present currently refuses Opaque; richer read-only Reveal would require a separately reviewed native/token identification interface and exact per-family labels/spans. Unknown byte preservation/refused presentation remains explicit; no universal working Reveal claim is made.

Original left/right gap mapping, selected default active styles and flat short-line states are available now. Long code streams, horizontal movement/wrap, vertical scroll/context keeping, repeated code labels, leading/trailing code windows, one-line/changed-height Reveal, custom blocked attributes, prompts/fullscreen menus/switching documents need their own original witnesses. Documentary intent to retain about five lines below the code cursor is not an implemented scroll algorithm. These are future finite discriminating questions after a concrete viewport decision, not a new guest grant now.

The user can judge today's clone by its functional shared code stream, but full visual/pane/catalogue parity remains unfinished M1. This proposal closes one visible omission with strong existing witnesses and keeps the rest visible.
