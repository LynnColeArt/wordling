## Specific available bytes and the principal trap

The original merge corpus contains DE subfunctions22 BREAK,30 ELSE,31 END FIELD,33 END IF,34 END RECORD,36 FIELD,3B IF BLANK,45 NEST PRIMARY,46 NEST SECONDARY,4D PAGE OFF and4E PAGE ON. These are native DE byte subfunctions, not WPM opcodes. All but END RECORD have observed L=4 frames (eight total bytes); END RECORD has L=6 (ten bytes) with observed stored counts2 or3. SDK51 WP86–87/PDF99–100 supports the command frame/operand distinctions and the count field; its date remains documentary context, not selected-executable proof. Preserve the original L+4 exception rather than imposing a prose nine-byte minimum.

Example: advanced04/CMD51-207 SECOND contains `Alice`, END FIELD,0A, END RECORD(count2), D4/00 formatter,0C, then Bob with the same structure. The conditional two-data-field fixture stores count3. Native count cannot simply be checked against the number of END FIELD markers or used as the number of substitute-able visible values. The reference secondary-file section describes the END FIELD/hard-return editing convention. WP50 must resolve exact structural versus field-content roles from the existing original source/capture/recipe and private manual passages, or return an explicit unsupported finding. Do not silently strip all hard returns, decrement every count, treat each0C as a record delimiter or assume all D4 functions are irrelevant. Captured0C exists in saved SECOND while default merged output uses its own copy-boundary behavior. The recorded IF BLANK branch is genuinely empty field2, not an absent/space-filled field equivalence proof.

Command arguments are outside the eight-byte DE command frame: e.g. FIELD is followed by ASCII `1~`, IF BLANK by `2~`, NEST by the captured native DOS filename and tilde. A frame parser that only assigns a subfunction name has not parsed those operands. Literal/delimiter tilde ambiguity, unknown operand contexts, names, malformed nesting and unobserved branches must remain distinguishable refusals/findings.

## Why this branch before the alternatives

Macro recording/compiler is still required M1. Existing original ABC recording and immutable WPM reader do not establish a generalized WPM writer, recording command boundaries, stop/error/cancel/editing contexts or description/index relocation. A bounded recorder could follow after its writer contract, but no current approved writer authority was found. WPM Compile is already implemented for a bounded execution subset; adding a second compiler would duplicate it. The merge reader has broader existing original witnesses and an independently executable next step without new guest activity.

Paragraph/Return, layout and complete printer-stream support remain high-value M1. WP14 observes0A/0D/8C/99 and complete streams; current document admission does not permit those mutations. WP49 is actively investigating the necessary rules and cannot be consumed before independent approval. A parallel speculative Return/layout implementation would overlap its unresolved authority. No hardware/resource blocker stops50; actual native serializer qualification later requires its exact field contract and reviewed original protocol. Physical terminal/historical DOS/graphics/non-US/font/dictionary resources remain real separate qualification gaps, not excuses to defer the independent read-only merge branch.

WB23/WB24 and merge-related WB25/WB28 remain uncovered full lessons; these scratch cases do not certify workbook datasets or teaching files. All remaining code/value-table commands, record options, conversion/utilities and errors remain visible follow-ups. This two-stage proposal makes no feature cuts and no generic-language compatibility claim.
