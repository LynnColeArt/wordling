## Remaining ambiguity that must not become invented defaults

1. **Width/placement:** The pages call it a character, but do not establish exact cell width, selected screen font mapping, attributes, cursor column/hit-test behavior, clipping at the last screen column, consecutive hard returns, or interaction with soft wraps/horizontal scroll/Reveal. Do not assume every Unicode marker occupies one cell, assign a pilcrow by habit, or claim original geometry from a terminal width function. A later declared WP identity/glyph mapping and focused actual original screen observations are needed for compatibility claims.
2. **Prompt/commit:** Exact prompt wording, key echo, acceptance of a typed marker (immediate versus Enter/F7), max encoded length, replacing an existing marker, and cancel after typing versus after returning to the parent are not described here. Generic F1 pending-cancel is documentary support, not proof that an already confirmed change rolls back across all Setup levels. Esc equivalence for this new prompt is not established by these manual pages. Preserve existing approved host mappings while documenting any adaptation explicitly.
3. **Persistence detail:** Cross-start persistence is explicit; precise disk-write timing, SET encoding/field, failure/backup/merge behavior and process/host scope are not specified by these pages. No checked original SET writer is supplied by this study. Initial absence/default must distinguish an explicit host choice from a measured original installation value.
4. **Character coverage:** Ctrl+2 means the original allows WP-set identities. A first bounded marker subset can only be an explicitly reviewed partial delivery with remaining identities open; ASCII-only or a chosen Unicode glyph cannot silently stand for full original support. No whole Compose/character-set expansion is authorized by this study.

Canonical CMD51-188 in docs/research/command-scenarios.json currently calls the feature Show Hard Returns, assumes a copied setup with the option disabled, and correctly remains documentary-draft/not-run/not-implemented with no evidence paths. Its naming is too informal to define the literal new menu. The actual original control is character configuration/Space clearing. ## Existing WP85 preference compatibility constraints

Read actual `internal/tui/everyday_settings.go`, runtime startup, opened-file platform guards, WP85 prompt and its approved settings-design/settings-review. The existing app preference is a separately reviewed host mapping for Menu Bar Remains Visible, not a generic native SET codec.

- Exact version1 bytes are `wordling-settings=1\nmenu_bar_remains_visible=yes\n` or the corresponding `no` form, and nothing else. The reader bounds input to header length+5, requires a regular retained file and accepts only those exact strings. Unknown versions/keys, appended marker fields, duplicates, malformed/extra bytes and missing values are not forward-compatible extensions; they refuse. The writer first reads/validates the existing file, then writes a complete single-key record via an exclusive0600 sibling, sync/close and rooted rename.
- Missing file/directory chooses Menu Bar visible=true without writing. That is the approved preview profile default, explicitly distinct from an original installation default. It says nothing about hard-return marker defaults.
- Preferences live under os.UserConfigDir()/wordling/settings, independent of document roots. Native bytes and original SET files are outside this host writer's authority. Unix nofollow/nonblock and Windows reparse checks remain safety boundaries.
- Approved WP85 behavior adopts a confirmed Menu Bar preference only after successful publication, retaining the prior active state and visible error on failure. No startup/open/cancel write; tests verify exact bytes, fresh Open/different roots, failures and no workspace listing pollution. This is not automatic proof of the new character prompt's exact original acceptance timing.
- A future persistent hard-return option needs a specifically reviewed, bounded backwards-compatible host-preference version/format/migration and concurrency/publication policy that preserves the existing Menu Bar key. Blindly appending a key or rewriting a v1 file from a new single-field value is incompatible. Alternatively, an explicitly reviewed session-only first delivery must keep persistence marked incomplete; it cannot claim the full original option complete. This is a choice for a later bounded plan, not an implementation requested here.
