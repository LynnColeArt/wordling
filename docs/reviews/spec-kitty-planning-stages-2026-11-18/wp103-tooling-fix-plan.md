# Held WP103 planning-stage repair plan

Audience: Spec Kitty core engineer and independent architecture reviewer. **PLAN ONLY.** The active b45 CLI, tool checkout, Wordling checkout/index/runtime, hosted state and original resources remain untouched. Read frozen tool AGENTS.md and charter first, including canonical authority, root-placement, affected-test scope, independent review and red-first requirements. No dispatch Op was opened. Actual implementation requires a separately authorized isolated source checkout and review; this document does not approve rolling out a replacement CLI during WP104.

## Decision

Keep physical planning placement on the canonical repository-root/PRIMARY partition, while allowing **separate dependency-ordered planning scheduling stages**. The earliest planning stage retains legacy lane-planning identity. A later stage receives a deterministic distinct scheduling ID but resolves to the same canonical root/target branch; it has no separately allocated branch/worktree. Planning WPs retain planning_artifact and their real dependencies. Do not delete103→86, relabel103, modify old99 status/prompts, filter completed dependencies from the graph, or suppress cycle checks.

This is not just a compute.py one-line fix. Existing ExecutionLane combines a scheduling vertex with workspace/branch identity, its model carries no explicit planning kind, and several consumers hardcode one planning ID. A complete bounded correction therefore needs a typed model/persistence and semantic-consumer amendment, with an architecture decision and compatibility tests. Existing semantic is_planning_lane/is_planning_artifact_only seams already anticipate changing the backing, so this need not become a second scheduler or generic new topology.

## Minimal scheduling algorithm

Preserve existing code overlap/surface union groups, code lane IDs and their internal WP topological order. Do not solve the separate problem of code contraction spanning an intervening planning dependency by silently splitting code ownership or removing its dependency.

1. Build a provisional graph from those existing code scheduling vertices **and one provisional vertex per planning WP**, with every authored dependency represented. Validate the original WP DAG and this complete provisional graph. A true WP cycle or a remaining code-contraction cycle still raises the existing structured error, with no writes.
2. Traverse that DAG in dependency-first deterministic order. Give code vertices the maximum stage value of their dependencies; give a planning vertex the maximum of dependency stage plus1 only for an incoming code→planning transition (zero for planning→planning), with empty max0. Thus early planning→code→late planning has planning stages0 and1. Code-only chains do not invent a stage per code WP.
3. Group planning WPs only when their computed stage values match; order members by the actual WP topological order with stable ID tie-breaking. The first occupied planning stage uses lane-planning, preserving all-planning, early-plan-only and the existing single late-plan-only fixtures. Further stages use bounded deterministic ASCII identifiers such as lane-planning-stage-2, with the number derived from sorted occupied stages, never authored overrides or Unicode sanitization. No classification by broad startswith alone.
4. Rebuild actual cross-vertex dependency edges from **all** WPs, then retain existing _find_lane_dependency_cycle and _compute_lane_depths checks. A cycle involving code→planning must strictly increase stage on that edge; regrouping equal planning stages cannot legitimately create such a backwards edge. Still validate the actual final graph instead of treating this reasoning as permission to skip a guard. Same-kind internal dependency order remains explicit.
5. Emit every WP exactly once, unchanged kind/dependencies and accurate planning-derived summary. For exact103, old early planning remains together;103 alone is downstream of86 and its05/21 predecessors. Existing code groups are unchanged. No membership inferred from status/approval history.

This algorithm closes the early/late planning contraction class while leaving true code-ownership scheduling conflicts visible. It is deliberately not a generic automatic lane-splitting/recovery service.

## Model/schema and older-CLI safety

Select an explicit typed per-vertex execution_mode and planning-stage identity in ExecutionLane, validated against actual member WP kinds. The planning_artifact_wps field remains a derived union across all planning stages; it is not new authority. LanesManifest.lane_for_wp remains the lookup owner. Reject duplicate membership, mixed-kind records, missing/nonexistent dependencies, invalid stage values and invalid new IDs before any allocation or write. Code lanes cannot claim root placement by spoofing a planning-like name.

An additive field/version bump alone is unsafe: frozen models.py:205 accepts data['version'] without checking supported versions, ignores unknown lane fields, and is_planning_lane recognizes only the old ID. An older CLI could therefore consume a new secondary planning vertex as a code workspace. **Do not call that backward compatibility.**

Minimal explicit persistence decision: retain exact version1 list encoding for manifests that need at most the legacy single planning stage. For a multistage manifest emit version2 with a required typed `execution_lanes` list and **omit legacy `lanes`**. New reader has one strict version switch (v1 adapter, v2 typed reader, unsupported version refusal); old b45 accesses data['lanes'], gets KeyError and existing read_lanes_json converts it to CorruptLanesError before allocator/branch effects. Test this against the real frozen reader, not a simulated version check it does not have. No dual list that an older reader can silently partially consume. The public in-memory manifest can retain `.lanes` as the single canonical semantic collection, with versioned serialization owned only by models/persistence.

Do not claim hosted support for this new local manifest contract without its separate external-contract owner review. For the initial local repair, require explicit per-invocation local mode and refuse multistage finalization when hosted sync is active before metadata writes; no global sync-disable patch. Existing v1 hosted behavior remains unchanged. This is a compatibility boundary, not a gate bypass.

## Mandatory R1/R2 review amendments (supersede ambiguous earlier shorthand)

Independent source review found two real boundaries that must be explicit. These corrections are part of the selected plan, not optional implementation choices.

### Shared-root planning propagation in mixed missions

Frozen `merge/executor.py:_phase_merge_lanes` skips planning at line448 only when the mission is planning-artifact-only. For mixed missions, `lanes/merge.py:consolidate_lane_into_mission` resolves the planning target and propagates it into the mission integration branch. Merely treating every planning stage as already integrated would drop that existing content path.

Preserve it: planning stages are distinct scheduling vertices sharing one physical target. At the existing mixed-mission integration boundary, resolve the actual explicit planning target and mission destination through typed context and retain the source identity under the existing merge operation's guards. Incorporate that shared source into a distinct mission branch once, idempotently, with normal ancestry/conflict/review/acceptance checks. Subsequent stages sharing that source/destination do not repeat the same merge. If source equals destination or is already contained, no self-merge occurs. No synthetic stage branch/worktree is created, deleted or rebased. Planning-only behavior remains its current target-direct no-op path.

Do not replace lane-allocation `planning_commit_sha` with a live target tip: it remains the frozen allocation ancestry input. Integration-time propagation of the fully reviewed current planning content is a separate existing concern. Resume must retain/check its actual source/destination identity and skip already-contained content without resetting a root ref.

Add a real temporary-Git mixed-mission test with target!=mission integration ref, an early planning commit, real code lane(s), and a late planning commit. Prove the integrated candidate contains the late artifact and final target integration retains it; assert the shared target is propagated at most once, root/target refs survive cleanup, and no synthetic stage branch or root self-merge occurs. Include target==destination, already-contained/retry/resume, conflict refusal and planning-only counterexamples. This verifies content conservation rather than just counting stages.
